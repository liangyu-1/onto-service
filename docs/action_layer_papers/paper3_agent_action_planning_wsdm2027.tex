\title{Ontology-Grounded Action Semantics for Policy-Constrained LLM Agents}

\author{Anonymous Authors\\Anonymous Institution}

\begin{document}
\maketitle

\begin{abstract}
LLM agents increasingly operate over tools that query and modify operational systems. Most tool-use interfaces, however, expose actions as flat function names with JSON arguments, leaving action semantics---target object classes, parameter roles, world-state preconditions, effects, confirmation requirements, and repair paths---implicit in prompts or documentation. This paper proposes an ontology-grounded action layer for policy-constrained LLM agents. The central claim is that agent planning should distinguish \emph{epistemic actions}, which acquire state and therefore require weak grounding, from \emph{mutating actions}, which change state and therefore require strong grounding, policy validation, and confirmation. We represent actions using a canonical ontology-grounded Action IR and compile it into an executable ActionBank containing action kind, grounding mode, target object type, parameter roles, preconditions, effects, and constraints. At runtime, the agent maintains an ontology state built only from the dialogue and observed tool outputs, checks candidate actions with type-aware admissibility rules, and repairs rejected proposals using ontology violation feedback. We instantiate the method on $\tau$-bench retail. The experimental protocol separates task success from mechanism evidence: task-level paired evaluation measures end-to-end utility, while ontology diagnostics measure role binding, state-sensitive admissibility, repair effectiveness, and failure modes.
\end{abstract}

\keywords{LLM agents, operational ontology, action layer, action semantics, action grounding, tool use}

\section{Introduction}
LLM agents are increasingly deployed as interfaces to operational systems rather than as text-only assistants. In these settings, an action is not merely a generated token sequence: it may query private records, modify an order, trigger a refund, schedule a service, or commit a workflow transition. The central problem is that most agents see actions as flat tool names with JSON arguments, while operational systems organize actions around domain objects, states, roles, constraints, effects, and workflow semantics. This paper studies how an ontology-grounded action layer can turn that implicit operational semantics into an explicit action model for LLM agents.

Many tool-use interfaces provide only a partial representation of this action semantics. Function names, JSON schemas, and natural-language tool descriptions specify how an API should be called, but they do not in general define which domain object the action targets, which object state makes it meaningful, which parameters fill which ontology roles, which state transition the action is expected to produce, or how the action relates to other actions in a workflow. For example, a schema can require an \texttt{order\_id}, but it does not by itself represent that \texttt{return\_delivered\_order\_items} is an action over an \textit{Order}, that it requires the order to be in a \textit{Delivered} state, that \texttt{item\_ids} are role fillers drawn from the order's item set, or that the effect is a transition toward a return-requested state. Recent agent benchmarks expose this gap: failures in $\tau$-bench, AppWorld, WorkArena, ToolSandbox, and DialogTool often involve state tracking, action grounding, policy following, and invalid tool execution rather than a complete absence of relevant tools~\cite{yao2024taubench,trivedi2024appworld,drouin2024workarena,lu2024toolsandbox,wang2025dialogtool}.

We study an \emph{action layer} as the executable part of an operational ontology. The action layer describes actions as first-class ontology-grounded entities: each action is connected to target object classes, parameter roles, state predicates, preconditions, effects, policy constraints, confirmation requirements, and execution-history predicates. Unlike an ontology used only as a passive knowledge source for retrieval, this layer supplies the semantic action space in which an LLM agent operates. It can be used to ground a proposed action to an ontology action type, bind arguments to object roles, infer eligible actions from current object states, check whether the proposed transition is meaningful, and explain why a proposal is or is not admissible.

The resulting question is broader than action blocking alone: does an ontology-grounded action model give an LLM agent a more structured operational semantics than a flat tool list? In our framework, the LLM proposes candidate actions, but the action layer provides the semantic substrate: it grounds arguments to domain objects, distinguishes actions that acquire state from actions that change state, checks preconditions and effects, and returns structured feedback when a proposal conflicts with the ontology. Verification is therefore one operational use of the action layer, not the whole contribution.

This framing is related to recent runtime enforcement systems that check LLM-agent actions against external rules, privilege policies, or formal constraints~\cite{wang2025agentspec,shi2025progent,kamath2025agentc,winston2026solver,sah2026verifiertax}. Our target representation differs: the constraints are embedded in an ontology-grounded action model that also defines object types, action roles, action kind, grounding mode, state predicates, and effects. We instantiate this design on the retail domain of $\tau$-bench, where agents must complete customer-service tasks under domain policies and stateful tool interactions~\cite{yao2024taubench}. The method should be interpreted as an ontology-grounded action semantics layer for agent planning and execution control, not merely as a verifier wrapped around tools.

The contributions of this paper are:
\begin{itemize}
    \item We define an \textbf{ontology-grounded action layer} for LLM agents, where executable actions are represented as ontology entities connected to target object classes, parameter roles, action kind, grounding mode, state predicates, preconditions, effects, policy constraints, and execution-history predicates.
    \item We introduce a \textbf{type-aware admissibility semantics} that separates epistemic actions with weak grounding from mutating actions with strong grounding. This distinction prevents the verifier from blocking the very read actions needed to acquire state, while still enforcing strict checks before state-changing actions.
    \item We operationalize the action layer in an agent loop through Action IR projection, runtime ontology-state tracking, type-aware admissibility checking, ontology-guided repair, and trace-based explanation.
    \item We provide a reproducible evaluation protocol on $\tau$-bench retail that separates task-success evidence from mechanism evidence, including role binding, state-sensitive admissibility, repair effectiveness, and repair-failure analysis.
\end{itemize}

\section{Related Work}
\subsection{LLM Agents and Tool Use}
Tool-using agents select and invoke external tools, APIs, or programs. Toolformer learns when and how to call APIs~\cite{schick2023toolformer}, ToolLLM constructs a large-scale tool-use benchmark and framework~\cite{qin2024toolllm}, and Gorilla connects LLMs with large API collections~\cite{patil2024gorilla}. Most tool-use systems rely on natural-language tool descriptions and input-output schemas. They often do not model domain-specific preconditions, effects, business rules, or state transitions in a formal action layer.

\subsection{Planning with Language Models}
LLMs can decompose goals into plans, but generated plans may be invalid or incomplete. ReAct shows that reasoning traces and actions can be interleaved~\cite{yao2023react}, while SayCan grounds language-model skill selection with affordance values in robotics~\cite{ahn2022saycan}. Existing methods improve planning with self-reflection, search, feedback, or external verifiers. Our approach is related, but the grounding object is different: instead of grounding skills only through learned affordance scores or natural-language tool descriptions, we ground agent actions in an ontology-defined action model containing object classes, state predicates, parameter roles, preconditions, and effects.

\subsection{Constraint Checking for LLM Agents}
Runtime enforcement systems and constraint checkers intercept agent actions and compare them with explicit specifications before execution. AgentSpec defines a domain-specific language for runtime constraints~\cite{wang2025agentspec}; Progent enforces tool-level privilege policies~\cite{shi2025progent}; Agent-C enforces temporal constraints over agent action sequences~\cite{kamath2025agentc}; and solver-aided policy checking translates tool-use policies into formal constraints for runtime verification~\cite{winston2026solver}. Recent empirical work also shows that strict verification can create a capability tradeoff: blocked actions may prevent invalid execution, but agents may fail to recover after intervention~\cite{sah2026verifiertax}. Our work uses verification, but the verifier is derived from ontology-grounded action semantics rather than from a standalone rule list. This matters because the same representation supports grounding, type-aware admissibility, effect explanation, and repair feedback.

\subsection{Agent Benchmarks for Realistic Workflows}
Recent benchmarks stress different aspects of agent planning. TravelPlanner evaluates multi-constraint travel planning~\cite{xie2024travelplanner}; $\tau$-bench evaluates tool-agent-user interaction under domain policies~\cite{yao2024taubench}; AppWorld evaluates interactive code-generating agents operating over many APIs~\cite{trivedi2024appworld}; WorkArena evaluates enterprise web tasks in ServiceNow-like environments~\cite{drouin2024workarena}; ToolSandbox evaluates stateful, conversational tool use~\cite{lu2024toolsandbox}; and DialogTool evaluates stateful tool use across multi-turn dialogues~\cite{wang2025dialogtool}. These benchmarks support our motivation: agent failure is often not only language understanding failure, but also action grounding, constraint tracking, state management, and long-horizon tool consistency failure.

\subsection{Ontology and Workflow Reasoning}
Ontologies and workflow models provide typed concepts, constraints, states, effects, and process relations. However, they are often used around LLM agents as retrieval context or documentation, not as the agent's executable action semantics. This paper treats the ontology action layer as the bridge between domain knowledge and tool use: it defines which actions exist, what objects they operate on, what states enable them, what effects they should have, and how those semantics can be checked and explained at runtime.

\section{Problem Definition}
Let $\mathcal{O}$ be an operational ontology with object types $\mathcal{T}$, state predicates $\mathcal{S}$, action types $\mathcal{A}$, parameter roles $\mathcal{R}$, constraints $\mathcal{C}$, and effect predicates $\mathcal{E}$. Given a user goal $g$, execution history $h_t$, and current state $s_t$, the agent must select an ontology-grounded action:
\[
\hat{a}_t(\hat{\theta}_t) = \operatorname{LLM}(g,h_t,s_t,\mathcal{A}),
\]
where $\hat{a}_t$ should be an action type in $\mathcal{A}$ and $\hat{\theta}_t$ should bind action roles to ontology objects or values. The action layer provides four semantic operations:
\[
\operatorname{Ground}(\hat{a}_t,\hat{\theta}_t,\mathcal{O}) \rightarrow a_t(\theta_t),
\]
\[
\operatorname{Enable}(a_t,\theta_t,s_t,h_t,\mathcal{O}) \rightarrow \{\operatorname{true},\operatorname{false}\},
\]
\[
\operatorname{Effect}(a_t,\theta_t,\mathcal{O}) \rightarrow \Delta s,
\]
\[
\operatorname{Explain}(a_t,\theta_t,s_t,h_t,\mathcal{O}) \rightarrow r.
\]
Grounding maps an LLM proposal to an ontology action and typed role fillers. Enabling checks whether the action is currently meaningful and executable. Effects describe the expected state transition. Explanation returns the ontology-level reason for acceptance or rejection. Runtime verification is one way to compose these semantic operations before execution:
\[
\operatorname{Verify}(\hat{a}_t,\hat{\theta}_t,s_t,h_t,\mathcal{O}) \rightarrow \{\operatorname{accept}, \operatorname{reject}(v)\},
\]
where $v$ is a structured violation reason such as unknown action, missing parameter, unsatisfied precondition, missing confirmation, policy violation, or duplicate action. If rejected, the agent receives $v$ and proposes a repair. A complete run produces an action sequence:
\[
\pi = [a_1(\theta_1), a_2(\theta_2), \ldots, a_m(\theta_m)]
\]
where each executed action has passed verification. A valid execution must satisfy:
\begin{itemize}
    \item every executed action is grounded to an action-layer schema;
    \item target objects and parameters are type-compatible;
    \item preconditions and confirmation requirements are satisfied at execution time;
    \item hard policy constraints are not violated;
    \item duplicate or unproductive repeated actions are blocked unless explicitly justified.
\end{itemize}
We call this representation \emph{ontology-grounded action semantics}. Admissibility is one predicate derived from it. The representation is stronger than API validity because it depends on semantic bindings between an action, its target object type, role fillers, object state, expected effects, domain policy, and execution history. It is weaker than full symbolic planning because the current implementation checks and repairs the proposed next action rather than searching over complete future plans. The paper evaluates whether this action semantics layer improves execution reliability and interpretability, and uses rejected-action traces to identify repair failure modes.

\section{Method}
\subsection{Overview}
The method fixes a narrow boundary. We do not propose a general agent optimizer, a benchmark-specific prompt recipe, or a hidden database retriever. The proposed system is an ontology-grounded action layer that sits between an LLM proposal and tool execution. Its input is a canonical Action IR or its runtime ActionBank projection; its runtime evidence is limited to the dialogue and tool outputs already observed in the trajectory; its output is either an admissible action call or a typed violation that can be used for repair.

The method has four components. First, Action IR construction represents each tool-level operation as a typed ontology action. Second, runtime ontology-state tracking converts observed tool outputs into object and state bindings. Third, type-aware admissibility checking applies different grounding rules to epistemic and mutating actions. Fourth, ontology-guided repair maps violations to productive next actions, such as querying missing state before attempting a state-changing operation.

\subsection{Action IR and ActionBank Representation}
The canonical Action IR is the shared representation between document-based action extraction and agent execution. It contains extraction-facing fields such as actor, evidence span, ontology grounding identifiers, and control-flow relations. ActionBank is the executable action ontology used by the agent and is compiled deterministically from this Action IR. It is not only a list of callable APIs. It is a typed action model that connects each tool-level operation to ontology concepts: action kind, grounding mode, target object class, parameter roles, enabling state predicates, expected effects, and policy constraints. The runtime projection of each action $a \in \mathcal{A}$ is represented as:
\[
a = \langle id, k, m, d, T_a, \Theta, P, E, C_a \rangle,
\]
where $id$ is the action identifier, $k$ is the action kind, $m$ is the grounding mode, $d$ is a natural-language description, $T_a$ is the target object type, $\Theta$ is the role schema for action parameters, $P$ is the set of enabling state predicates, $E$ is the set of expected effects, and $C_a$ is the set of hard policy constraints. The full Action IR also keeps evidence and grounding fields, but these are not sent directly to the official tool executor; they are retained for audit, extraction evaluation, and cross-paper consistency.

The key representation choice is the pair $(k,m)$. In the current method, $k \in \{\textit{epistemic}, \textit{mutate}, \textit{compute}, \textit{confirm}, \textit{transfer}, \textit{finish}\}$ and $m \in \{\textit{weak}, \textit{strong}\}$. Epistemic actions, such as user lookup, order lookup, product lookup, and catalog listing, acquire state and therefore use weak grounding. Mutating actions, such as cancellation, return, exchange, address modification, and payment modification, change state and therefore use strong grounding. This distinction is not benchmark-specific: in another domain, an inspection, search, diagnosis, or measurement action would normally be epistemic, while a repair, approval, update, submission, or actuation action would normally be mutating.

For example, \texttt{get\_order\_details} is an epistemic action over an \textit{Order}. It requires a concrete \texttt{order\_id} and authentication, but it must not require the order to already be cached; its purpose is to acquire that state. In contrast, \texttt{return\_delivered\_order\_items} is a mutating action over an observed \textit{Order}. Its \texttt{order\_id} role must bind to an observed order individual, \texttt{item\_ids} must bind to items contained in that order, and \texttt{payment\_method\_id} must bind to an available refund method. The enabling predicate is that the order is in the \textit{Delivered} state; the effect is a transition toward a return-requested state.

\subsection{Runtime Ontology State}
The agent maintains a compact grounded state $s_t$ that maps dialogue facts and observed tool results to ontology individuals and state predicates. In the retail setting, $s_t$ includes authentication status, the authenticated user id, observed users, observed orders, observed products, observed variants, observed payment methods, confirmation status, and a record of whether a final update action has already been taken on an order. The execution history $h_t$ stores accepted actions, arguments, results, verifier decisions, and repair attempts.

The LLM receives a textual abstraction of this grounded state rather than direct database access. This restriction is part of the method boundary: the agent may not read the complete benchmark database or any hidden environment state. It can only use the user dialogue, official tool outputs already observed in the trajectory, and the ActionBank schema. This makes the grounding mechanism auditable and prevents leakage from the evaluator into the planner.

\subsection{Action Proposal}
At step $t$, the LLM proposes a JSON action call:
\[
\hat{a}_t(\hat{\theta}_t) = \operatorname{LLM}(g,h_t,\phi(s_t),\mathcal{A}),
\]
where $\phi(s_t)$ is the compact ontology-grounded state abstraction. The prompt contains the ActionBank schemas, recent execution history, and observed object summaries. The LLM is therefore asked to choose within a semantically structured action space. It is not trusted as the final authority on executability; its output is treated as a candidate action instance that must be grounded and checked.

\subsection{Type-Aware Admissibility}
Given a proposed action $\hat{a}_t(\hat{\theta}_t)$, the verifier applies five checks:
\[
V = V_{\text{exist}} \wedge V_{\text{param}} \wedge V_{\text{pre}} \wedge V_{\text{policy}} \wedge V_{\text{dup}}.
\]
\textbf{Action existence} checks whether the action id is present in ActionBank. \textbf{Parameter checking} verifies that required arguments are present and type-compatible when the type can be checked locally. \textbf{Precondition checking} evaluates state predicates such as \texttt{order.status == pending} or \texttt{order.status == delivered}. \textbf{Policy checking} enforces hard business rules such as user authentication and explicit confirmation before update actions. \textbf{Duplicate checking} rejects repeated information-gathering actions with identical arguments when a previous execution has already succeeded.

The verifier is type-aware. For an epistemic action with weak grounding, the verifier checks action existence, required identifiers, authentication if required, placeholder values, and duplicate calls. It does not require the target object to already be observed, because the action's purpose is to observe it. For a mutating action with strong grounding, the verifier additionally requires observed target objects, role-bound arguments, state preconditions, policy constraints, and explicit confirmation. Formally:
\[
\operatorname{Adm}(a,\theta,s_t) =
\begin{cases}
V_{\text{exist}}\wedge V_{\text{param}}\wedge V_{\text{policy}}\wedge V_{\text{dup}}, & m(a)=\textit{weak},\\
V_{\text{exist}}\wedge V_{\text{param}}\wedge V_{\text{ground}}\wedge V_{\text{pre}}\wedge V_{\text{policy}}\wedge V_{\text{dup}}, & m(a)=\textit{strong}.
\end{cases}
\]
This distinction is the central method contribution. A uniform strong verifier blocks useful read actions and prevents the agent from acquiring the very state needed for safe mutation. A uniform weak verifier permits unsafe updates. Type-aware admissibility resolves this tension by treating state-acquisition and state-changing actions differently.

The verifier returns either \texttt{accept} or \texttt{reject} with typed violations such as \textsc{UnknownAction}, \textsc{MissingParameter}, \textsc{Grounding}, \textsc{Precondition}, \textsc{Policy}, \textsc{Duplicate}, or \textsc{PrematureTransfer}.

This admissibility check is ontology-grounded in the following sense. The action id is resolved against an ontology action type, the target is checked against an ontology object class, the parameters are interpreted as typed role fillers, preconditions and effects are attached to object-state predicates, and policy constraints are represented as action-level guards. The verifier therefore does not merely ask whether the JSON call is syntactically valid; it asks whether the proposed operation is semantically meaningful for the target object in the current execution context.

\subsection{Ontology-Guided Repair}
If verification fails, the proposed action is not executed and is not added to the successful execution trace. Instead, the system appends structured violation feedback to the prompt:
\[
( \hat{a}_t, \hat{\theta}_t, v, \phi(s_t), h_t ) \rightarrow \operatorname{repair\ prompt}.
\]
The repair prompt asks the LLM to propose a different productive action that satisfies all constraints. Repair is defined over ontology violation types rather than over benchmark-specific tool names. Missing authentication maps to an authentication lookup; unknown order state maps to an order-detail query; unknown product variant maps to product-detail or catalog query; missing confirmation maps to confirmation; premature transfer maps to a recoverable prerequisite action if one exists. For example, a rejected cancellation with \textsc{OrderStatusUnverified} should repair to an epistemic \texttt{get\_order\_details} action before any mutating action is attempted.

Repair is bounded by a small retry budget. If no valid action is found and no admissible epistemic or mutating repair path remains, the agent may transfer to a human agent. This fallback is conservative, but it can also reduce task success when the repair policy is weak. We therefore evaluate repair behavior separately from raw task success.

\subsection{Repair Failure Analysis}
The same verifier trace is used to analyze repair behavior. For every rejected proposal, we record the rejected action, violation type, repaired action, whether the repaired action is accepted, and whether the final task outcome improves, remains unchanged, or degrades relative to Schema-Only. We classify repair outcomes into four categories:
\begin{itemize}
    \item \textbf{productive repair}: rejection causes the agent to choose a valid action that advances the task;
    \item \textbf{neutral repair}: rejection removes a violation but does not change final task failure;
    \item \textbf{over-correction}: rejection causes the agent to abandon a recoverable trajectory, usually by transferring to a human agent;
    \item \textbf{state-insensitive repair}: the repaired action remains incompatible with a counterfactual or dialogue-dependent state even though it passes local checks.
\end{itemize}
This analysis is necessary because local ontology consistency and task success are different properties. The evaluation therefore reports both executed violations and repair-induced outcome changes rather than treating successful verification as automatically beneficial for task completion.

\subsection{Execution Trace and Explanation}
For each episode, the system records accepted actions, rejected actions, violation types, repair attempts, and execution results. This trace supports two uses. First, it is used by the duplicate detector and state abstraction module. Second, it provides faithful explanations: the system can explain that an action was blocked because it repeated an already successful lookup, lacked user confirmation, or violated an order-status precondition. The explanation is therefore derived from verifier traces rather than generated as an unconstrained post-hoc rationale.

\section{Experimental Setup}
\subsection{Dataset}
We evaluate on the retail domain of $\tau$-bench~\cite{yao2024taubench}, a customer-service benchmark. The retail domain contains 500 users, 50 products, and 1,000 orders with tool actions for authentication, query, cancellation, return, exchange, and modification. Each task provides a user scenario, evaluation criteria, and a gold action sequence. We use the official train/test split (74 train / 40 test tasks for retail).

$\tau$-bench is useful because it provides realistic stateful tool-use workflows, but it is not by itself sufficient to prove the ontology-specific claim of this paper. A high or low task score could be caused by language understanding, dialogue branching, model capability, simulator mismatch, or repair behavior. We therefore use $\tau$-bench in two complementary ways. First, the official retail test split is the end-to-end workflow benchmark. Second, we derive an ontology benchmark suite from the same domain objects, policies, tool schemas, and database states. The derived suite isolates whether the proposed action layer improves epistemic-action preservation, strong grounding for mutating actions, argument-role binding, and repair effectiveness.

The canonical Action IR additionally stores actor, target binding, evidence, grounding identifiers, state transitions, and control-flow hints. \subsection{Benchmark Design}
The evaluation is organized around two questions. The first question is whether the agent completes realistic $\tau$-bench retail workflows. The second question is whether the ontology action layer contributes semantic information beyond ordinary tool schemas. The second question requires targeted tests, because ordinary task success does not reveal whether a model used object types, state predicates, role schemas, or effects.

Each case fixes the user goal and perturbs one ontology variable, such as order state, target object type, role filler, or expected effect. This produces controlled pairs where a flat tool list gives nearly the same surface prompt, but the ontology action layer should change the admissible or preferred action.

The type-aware admissibility benchmark is the most direct test of the paper's ontology claim. For example, a concrete \texttt{order\_id} should be sufficient for an authenticated \texttt{get\_order\_details} call, because that epistemic action acquires state. The same \texttt{order\_id} is not sufficient for \texttt{return\_delivered\_order\_items}, because that mutating action requires an observed delivered order, item-role binding, payment binding, and user confirmation. A flat tool schema does not express this distinction.

The argument-role and effect-consistency benchmarks test complementary parts of the representation. Role binding asks whether \texttt{order\_id}, \texttt{item\_ids}, \texttt{new\_item\_ids}, and \texttt{payment\_method\_id} bind to valid ontology individuals in the correct relation. Effect consistency asks whether the action selected by the agent corresponds to the intended state transition. Together, these tests show that ActionBank represents domain action semantics, not only blocking rules.

\subsection{Baselines and Ablations}
\textbf{Schema-Only}: The agent receives the official tool schemas, domain policy, and conversation history. It does not use ActionBank, runtime ontology state, type-aware admissibility, or ontology-guided repair.

\textbf{Ontology-Prompt}: The agent receives ActionBank descriptions in the prompt, but no runtime admissibility checker. This tests whether action semantics as context alone is sufficient.

\textbf{State-Only}: The agent receives ActionBank plus the runtime ontology state reconstructed from observed tool outputs, but no blocking verifier. This isolates the value of explicit state abstraction.

\textbf{Typed-Admissibility}: State-Only plus type-aware admissibility checking. Epistemic actions use weak grounding and mutating actions use strong grounding. This isolates the central admissibility semantics.

\textbf{Typed-Admissibility+Repair}: Typed-Admissibility plus ontology-guided repair feedback. This is the full method used for the main comparison.

\textbf{Ablations}: We remove one semantic component at a time: \textsc{NoActionKind} applies one uniform grounding rule to all actions; \textsc{NoRuntimeState} removes observed object summaries; \textsc{NoRepair} blocks invalid actions without repair; \textsc{NoRoleGrounding} removes semantic parameter-role checks. These ablations are designed to test the method claim rather than to optimize a benchmark score.

\subsection{Models}
The current implementation uses an OpenAI-compatible LLM endpoint with temperature set to 0. The model is held fixed across Schema-Only and ontology variants. Model choice is not the contribution of this paper; all claims require paired comparisons under the same model, task split, number of trials, maximum steps, and user simulator.

\subsection{Metrics}
\textbf{Official Task Success}: Official $\tau$-bench reward on paired task/trial keys.
\textbf{Executed Violation Rate}: Number of invalid mutating actions that reach the tool executor.
\textbf{Rejected Violation Count}: Number and type of candidate actions rejected before execution.
\textbf{Epistemic Preservation}: Fraction of valid read/lookup actions allowed under weak grounding. This metric detects over-constraining verifiers that block state acquisition.
\textbf{Strong-Grounding Compliance}: Fraction of mutating actions whose target objects, item roles, payment roles, state preconditions, and confirmation requirements are satisfied before execution.
\textbf{Repair Outcome}: Whether a rejected action leads to productive repair, neutral repair, over-correction, or unrecovered failure.
\textbf{Repair Path Accuracy}: Whether violation types map to the expected epistemic or confirmation repair action.
\textbf{Latency}: Average wall-clock time and tool-call count per task.
\textbf{Ablation Delta}: Performance change after removing action kind, runtime state, role grounding, or repair.

\section{Results}
\subsection{Current Run Status}

We do not yet report a final task-performance claim. Pilot runs exposed an important method-level failure mode: applying strong grounding uniformly to both epistemic and mutating actions can collapse task performance because lookup actions such as order and product reads are blocked before the agent can acquire state. This failure motivates the type-aware admissibility semantics introduced in this paper. A paper-eligible run must therefore use the corrected ActionBank projection with \texttt{action\_kind} and \texttt{grounding\_mode}, must avoid hidden database access, and must complete paired Schema-Only and ontology runs on the same task/trial keys.

A run is considered valid only if: (1) the same model, user simulator, split, number of trials, and maximum step budget are used for all compared methods; (2) all requested task/trial keys are paired; (3) no hidden environment database is read by the agent; (4) ontology traces include accepted actions, rejected actions, violation types, grounding changes, and repair outcomes; and (5) aggregate numbers are computed from official $\tau$-bench rewards rather than from partial runs.

\subsection{Implementation Checks}

The symbolic components are tested independently of the LLM. The assertion-based checks cover the following admissibility cases:
\begin{itemize}
    \item update action without authentication is rejected by a policy constraint;
    \item return action on a pending order is rejected by an order-status precondition;
    \item exchange action without user confirmation is rejected by a confirmation constraint;
    \item correctly authenticated and confirmed cancellation of a pending order is accepted;
    \item duplicate successful lookup and unknown action ids are rejected.
    \item epistemic read actions with concrete identifiers are not rejected merely because the target object has not yet been cached;
    \item mutating actions still require observed target objects, valid state, and confirmation.
\end{itemize}
These checks validate the implementation of the admissibility predicate, but they do not by themselves establish task-level agent performance. They are therefore reported as implementation validation rather than as benchmark results.

\subsection{Planned End-to-End Table}

After a valid paired run, the main table should compare \textsc{Schema-Only}, \textsc{Ontology-Prompt}, \textsc{State-Only}, \textsc{Typed-Admissibility}, and \textsc{Typed-Admissibility+Repair}. The table columns should report official reward, executed violation rate, epistemic preservation, strong-grounding compliance, repair outcome distribution, tool-call count, and latency.

This table is necessary but not sufficient for the ontology claim. It shows whether the full system helps on realistic workflows, but it does not isolate why. Until the corrected type-aware run is completed, we avoid claiming that the method improves task success. The current paper claim is therefore methodological: the proposed action layer defines an inspectable ontology action semantics and an evaluation protocol that separates ontology grounding, execution compliance, repair behavior, and task completion.

\subsection{Qualitative Trace Analysis}

The trace format supports qualitative analysis once a valid model run is available. For each task, the logs record the proposed action, verifier decision, violation type, repair attempts, grounding changes, execution result, and official task outcome. The intended qualitative analysis is to separate four cases: (1) weak grounding preserves a useful epistemic action; (2) strong grounding blocks an unsafe mutating action and repair recovers progress; (3) strong grounding blocks a harmful action but the model fails to recover; and (4) the repair policy over-corrects and causes premature transfer.

\section{Discussion}
\subsection{What the Action Layer Contributes}
The primary value of the action layer is not higher autonomous planning success by itself. Its value is to provide an ontology-grounded semantics for agent actions. Compared with ordinary tool schemas, the action layer binds actions to ontology object types, parameter roles, state predicates, confirmation requirements, policy guards, effects, and execution-history predicates. This gives the agent a structured action space: it can ask which actions are meaningful for the current object state, what role each argument plays, what state transition the action should produce, and why a proposed action is inconsistent with the ontology.

This distinction also separates the proposed method from generic tool filtering. A filter can allow or deny a tool name; an ontology-grounded action layer represents the operation as a domain action over typed objects with action kind, grounding mode, preconditions, and effects. The verifier is only one consumer of that representation. The same action layer also supports argument grounding, state-aware prompting, repair feedback, and explanation. The key design principle is that agent planning should be grounded in domain actions and object states, not only in API syntax.

\subsection{Why Repair Requires a Separate Policy}
Ontology-grounded admissibility is a local semantic predicate: it can say why a proposed action is not meaningful in the current context, but it does not by itself choose the globally best next action. Post-rejection behavior is therefore a separate policy problem. In simple cases, the violation feedback maps directly to a local fix, such as inserting confirmation or using cached lookup results. In harder cases, the LLM may over-correct, abandon a recoverable trajectory, or choose an admissible action that is still wrong for the task. This suggests that future systems need a stronger repair policy, such as candidate-action ranking under admissibility constraints, state-machine-guided repair, or search over admissible actions, rather than relying only on a single LLM repair prompt.

\subsection{Limitations}
\textbf{Model capability.} The framework does not assume that the LLM is a reliable planner. The verifier can reject non-admissible local actions, but it cannot by itself infer the globally correct branch in a task with incomplete dialogue state or ambiguous user intent. Valid task-performance claims therefore require a clean model run and paired comparison against Schema-Only.

\textbf{Dialogue simulation.} $\tau$-bench tasks require back-and-forth dialogue for condition branching and user confirmation. Our evaluation therefore uses the official simulator for task success. Ontology checks remain local semantic checks; they cannot by themselves infer the globally correct branch in an underspecified dialogue.

\textbf{Repair overhead.} The repair loop increases latency because rejected proposals require additional LLM calls. Future experiments should report both ontology-consistency benefits and latency cost.

\textbf{Action layer completeness.} The proposed method depends on an action layer with explicit object classes, action types, role schemas, state predicates, preconditions, effects, and constraints. Many real systems lack such representations, motivating companion work on action extraction from procedural documents.

\subsection{Future Work}
We plan to: (1) run full paired $\tau$-bench evaluations with the corrected type-aware ActionBank; (2) conduct larger-scale counterfactual state tests to measure epistemic preservation and strong-grounding compliance; (3) extend to the airline and industrial SOP domains; (4) learn neural repair policies to complement rule-based checks; and (5) distinguish hard constraints from soft preferences.

\section{Conclusion}
This paper frames policy-constrained tool use as ontology-grounded action semantics for LLM agents. By representing operations as typed ontology actions with action kind, grounding mode, object bindings, role schemas, state predicates, preconditions, effects, constraints, confirmation requirements, and execution-history predicates, the action layer gives the agent more than a flat tool list. It distinguishes epistemic actions that acquire state from mutating actions that change state, applies type-aware admissibility, and provides ontology-guided repair feedback. The framework should therefore be understood as an ontology action layer for agent planning and execution, not merely as a verifier wrapped around tools.
