\title{Ontology-Grounded Action Semantics for Policy-Constrained LLM Agents}

\author{Anonymous Authors\\Anonymous Institution}

\begin{document}
\maketitle

\begin{abstract}
LLM agents increasingly interact with tools, databases, workflows, and operational environments. However, many agents still operate over a flat action space: actions are represented as tool names with JSON arguments, while the domain semantics of those actions---target object classes, parameter roles, state predicates, preconditions, effects, and workflow constraints---remain implicit in documentation or prompts. This paper studies an ontology-grounded action layer for LLM agents. We represent executable operations as an ActionBank in which actions are first-class ontology entities connected to object types, role schemas, enabling states, effects, policy constraints, confirmation requirements, and execution-history predicates. The action layer supports action grounding, state-derived affordance generation, admissibility verification, bounded repair, and trace-based explanation. Verification is therefore one operational use of the ontology action semantics rather than the whole framework. We instantiate the framework on $\tau$-bench retail and propose a dedicated ontology benchmark suite that measures state-sensitive affordance selection, argument-role binding, effect consistency, and ontology-component ablations. The current draft contributes the method and implementation protocol; aggregate task-performance claims require a clean rerun of the corrected LLM client and audited raw traces.
\end{abstract}

\keywords{LLM agents, operational ontology, action layer, action semantics, action grounding, tool use}

\section{Introduction}
LLM agents are increasingly deployed as interfaces to operational systems rather than as text-only assistants. In these settings, an action is not merely a generated token sequence: it may query private records, modify an order, trigger a refund, schedule a service, or commit a workflow transition. The central problem is that most agents see actions as flat tool names with JSON arguments, while operational systems organize actions around domain objects, states, roles, constraints, effects, and workflow semantics. This paper studies how an ontology-grounded action layer can turn that implicit operational semantics into an explicit action model for LLM agents.

Many tool-use interfaces provide only a partial representation of this action semantics. Function names, JSON schemas, and natural-language tool descriptions specify how an API should be called, but they do not in general define which domain object the action targets, which object state makes it meaningful, which parameters fill which ontology roles, which state transition the action is expected to produce, or how the action relates to other actions in a workflow. For example, a schema can require an \texttt{order\_id}, but it does not by itself represent that \texttt{return\_delivered\_order\_items} is an action over an \textit{Order}, that it requires the order to be in a \textit{Delivered} state, that \texttt{item\_ids} are role fillers drawn from the order's item set, or that the effect is a transition toward a return-requested state. Recent agent benchmarks expose this gap: failures in $\tau$-bench, AppWorld, WorkArena, ToolSandbox, and DialogTool often involve state tracking, action grounding, policy following, and invalid tool execution rather than a complete absence of relevant tools~\cite{yao2024taubench,trivedi2024appworld,drouin2024workarena,lu2024toolsandbox,wang2025dialogtool}.

We study an \emph{action layer} as the executable part of an operational ontology. The action layer describes actions as first-class ontology-grounded entities: each action is connected to target object classes, parameter roles, state predicates, preconditions, effects, policy constraints, confirmation requirements, and execution-history predicates. Unlike an ontology used only as a passive knowledge source for retrieval, this layer supplies the semantic action space in which an LLM agent operates. It can be used to ground a proposed action to an ontology action type, bind arguments to object roles, infer eligible actions from current object states, check whether the proposed transition is meaningful, and explain why a proposal is or is not admissible.

The resulting question is broader than action blocking alone: does an ontology-grounded action model give an LLM agent a more structured operational semantics than a flat tool list? In our framework, the LLM proposes candidate actions, but the action layer provides the semantic substrate: it narrows the action space to ontology-defined operations, grounds arguments to domain objects, exposes state-dependent affordances, checks preconditions and effects, and returns structured feedback when a proposal conflicts with the ontology. Verification is therefore one operational use of the action layer, not the whole contribution.

This framing is related to recent runtime enforcement systems that check LLM-agent actions against external rules, privilege policies, or formal constraints~\cite{wang2025agentspec,shi2025progent,kamath2025agentc,winston2026solver,sah2026verifiertax}. Our target representation differs: the constraints are embedded in an ontology-grounded action model that also defines object types, action roles, state predicates, effects, and action affordances. We instantiate this design on the retail domain of $\tau$-bench, where agents must complete customer-service tasks under domain policies and stateful tool interactions~\cite{yao2024taubench}. The method should be interpreted as an ontology-grounded action semantics layer for agent planning and execution control, not merely as a verifier wrapped around tools.

The contributions of this paper are:
\begin{itemize}
    \item We define an \textbf{ontology-grounded action layer} for LLM agents, where executable actions are represented as ontology entities connected to target object classes, parameter roles, state predicates, preconditions, effects, policy constraints, and execution-history predicates.
    \item We instantiate an ActionBank for $\tau$-bench retail that turns the benchmark's flat tools into typed ontology-grounded actions with explicit object bindings and state-transition semantics.
    \item We operationalize the action layer in an agent loop through action grounding, state-derived affordance generation, admissibility verification, bounded repair, and trace-based explanation.
    \item We provide a reproducible evaluation protocol on the 40-task $\tau$-bench retail test split and a companion ontology benchmark suite for state-sensitive affordance selection, role binding, effect consistency, and ontology-component ablations. This protocol separates ontology-semantics evidence, execution-compliance evidence, and task-success evidence.
\end{itemize}

\section{Related Work}
\subsection{LLM Agents and Tool Use}
Tool-using agents select and invoke external tools, APIs, or programs. Toolformer learns when and how to call APIs~\cite{schick2023toolformer}, ToolLLM constructs a large-scale tool-use benchmark and framework~\cite{qin2024toolllm}, and Gorilla connects LLMs with large API collections~\cite{patil2024gorilla}. Most tool-use systems rely on natural-language tool descriptions and input-output schemas. They often do not model domain-specific preconditions, effects, business rules, or state transitions in a formal action layer.

\subsection{Planning with Language Models}
LLMs can decompose goals into plans, but generated plans may be invalid or incomplete. ReAct shows that reasoning traces and actions can be interleaved~\cite{yao2023react}, while SayCan grounds language-model skill selection with affordance values in robotics~\cite{ahn2022saycan}. Existing methods improve planning with self-reflection, search, feedback, or external verifiers. Our approach is related, but the grounding object is different: instead of grounding skills only through learned affordance scores or natural-language tool descriptions, we ground agent actions in an ontology-defined action model containing object classes, state predicates, parameter roles, preconditions, and effects.

\subsection{Constraint Checking for LLM Agents}
Runtime enforcement systems and constraint checkers intercept agent actions and compare them with explicit specifications before execution. AgentSpec defines a domain-specific language for runtime constraints~\cite{wang2025agentspec}; Progent enforces tool-level privilege policies~\cite{shi2025progent}; Agent-C enforces temporal constraints over agent action sequences~\cite{kamath2025agentc}; and solver-aided policy checking translates tool-use policies into formal constraints for runtime verification~\cite{winston2026solver}. Recent empirical work also shows that strict verification can create a capability tradeoff: blocked actions may prevent invalid execution, but agents may fail to recover after intervention~\cite{sah2026verifiertax}. Our work uses verification, but the verifier is derived from ontology-grounded action semantics rather than from a standalone rule list. This matters because the same representation supports grounding, affordance generation, effect explanation, and repair feedback.

\subsection{Agent Benchmarks for Realistic Workflows}
Recent benchmarks stress different aspects of agent planning. TravelPlanner evaluates multi-constraint travel planning~\cite{xie2024travelplanner}; $\tau$-bench evaluates tool-agent-user interaction under domain policies~\cite{yao2024taubench}; AppWorld evaluates interactive code-generating agents operating over many APIs~\cite{trivedi2024appworld}; WorkArena evaluates enterprise web tasks in ServiceNow-like environments~\cite{drouin2024workarena}; ToolSandbox evaluates stateful, conversational tool use~\cite{lu2024toolsandbox}; and DialogTool evaluates stateful tool use across multi-turn dialogues~\cite{wang2025dialogtool}. These benchmarks support our motivation: agent failure is often not only language understanding failure, but also action grounding, constraint tracking, state management, and long-horizon tool consistency failure.

\subsection{Ontology and Workflow Reasoning}
Ontologies and workflow models provide typed concepts, constraints, states, effects, and process relations. However, they are often used around LLM agents as retrieval context or documentation, not as the agent's executable action semantics. This paper treats the ontology action layer as the bridge between domain knowledge and tool use: it defines which actions exist, what objects they operate on, what states enable them, what effects they should have, and how those semantics can be checked and explained at runtime.

\section{Problem Definition}
Let $\mathcal{O}$ be an operational ontology with object types $\mathcal{T}$, state predicates $\mathcal{S}$, action types $\mathcal{A}$, parameter roles $\mathcal{R}$, constraints $\mathcal{C}$, and effect predicates $\mathcal{E}$. Given a user goal $g$, execution history $h_t$, and current state $s_t$, the agent must select an ontology-grounded action:
\[
\hat{a}_t(\hat{\theta}_t) = \operatorname{LLM}(g,h_t,s_t,\mathcal{A}),
\]
where $\hat{a}_t$ should be an action type in $\mathcal{A}$ and $\hat{\theta}_t$ should bind action roles to ontology objects or values. The action layer provides four semantic operations:
\[
\operatorname{Ground}(\hat{a}_t,\hat{\theta}_t,\mathcal{O}) \rightarrow a_t(\theta_t),
\]
\[
\operatorname{Enable}(a_t,\theta_t,s_t,h_t,\mathcal{O}) \rightarrow \{\operatorname{true},\operatorname{false}\},
\]
\[
\operatorname{Effect}(a_t,\theta_t,\mathcal{O}) \rightarrow \Delta s,
\]
\[
\operatorname{Explain}(a_t,\theta_t,s_t,h_t,\mathcal{O}) \rightarrow r.
\]
Grounding maps an LLM proposal to an ontology action and typed role fillers. Enabling checks whether the action is currently meaningful and executable. Effects describe the expected state transition. Explanation returns the ontology-level reason for acceptance or rejection. Runtime verification is one way to compose these semantic operations before execution:
\[
\operatorname{Verify}(\hat{a}_t,\hat{\theta}_t,s_t,h_t,\mathcal{O}) \rightarrow \{\operatorname{accept}, \operatorname{reject}(v)\},
\]
where $v$ is a structured violation reason such as unknown action, missing parameter, unsatisfied precondition, missing confirmation, policy violation, or duplicate action. If rejected, the agent receives $v$ and proposes a repair. A complete run produces an action sequence:
\[
\pi = [a_1(\theta_1), a_2(\theta_2), \ldots, a_m(\theta_m)]
\]
where each executed action has passed verification. A valid execution must satisfy:
\begin{itemize}
    \item every executed action is grounded to an action-layer schema;
    \item target objects and parameters are type-compatible;
    \item preconditions and confirmation requirements are satisfied at execution time;
    \item hard policy constraints are not violated;
    \item duplicate or unproductive repeated actions are blocked unless explicitly justified.
\end{itemize}
We call this representation \emph{ontology-grounded action semantics}. Admissibility is one predicate derived from it. The representation is stronger than API validity because it depends on semantic bindings between an action, its target object type, role fillers, object state, expected effects, domain policy, and execution history. It is weaker than full symbolic planning because the current implementation checks and repairs the proposed next action rather than searching over complete future plans. The paper evaluates whether this action semantics layer improves execution reliability and interpretability, and uses rejected-action traces to identify repair failure modes.

\section{Method}
\subsection{Overview}
The proposed framework separates language-level action proposal from ontology-level action semantics. The LLM reads the user goal and proposes a candidate action, but the action layer defines what that candidate means in the domain: which action type it instantiates, which object class it targets, which role each argument fills, which state predicates enable it, and which effect it is expected to produce. Verification, affordance generation, repair, and explanation are then built on top of this shared action semantics.

\subsection{ActionBank Representation}
ActionBank is the executable action ontology used by the agent. It is not only a list of callable APIs. It is a typed action model that connects each tool-level operation to ontology concepts: target object class, parameter roles, enabling state predicates, expected effects, and policy constraints. Each action $a \in \mathcal{A}$ is represented as:
\[
a = \langle id, d, T_a, \Theta, P, E, C_a \rangle,
\]
where $id$ is the action identifier, $d$ is a natural-language description, $T_a$ is the target object type, $\Theta$ is the role schema for action parameters, $P$ is the set of enabling state predicates, $E$ is the set of expected effects, and $C_a$ is the set of hard policy constraints. This representation differs from ordinary tool descriptions in three ways. First, actions are typed by the ontology object class they operate on. Second, parameters are interpreted as semantic roles rather than anonymous JSON fields. Third, preconditions and effects connect an action to the domain state transition it represents.

For example, \texttt{return\_delivered\_order\_items} is an ontology action over an \textit{Order}. Its \texttt{order\_id} role must bind to an order individual, \texttt{item\_ids} must bind to items contained in that order, and \texttt{payment\_method\_id} must bind to an available refund method. The enabling predicate is that the order is in the \textit{Delivered} state; the effect is a transition toward a return-requested state. The current implementation uses effects for explanation and local DB-state replay, while future work can use the same effect representation for symbolic search.

\subsection{Object and State Grounding}
The agent maintains a compact grounded state $s_t$ that maps dialogue facts and tool results to ontology individuals and state predicates. In the retail setting, $s_t$ includes authentication status, the authenticated user id, cached users, cached orders, cached product records, confirmation status, and a record of whether a final update action has already been taken on an order. The execution history $h_t$ stores accepted actions, arguments, results, verifier decisions, and repair attempts.

The LLM receives a textual abstraction of this grounded state rather than direct database access. In addition to raw cached object identifiers, the prompt includes ontology-derived object summaries such as order status, available payment methods, item-role bindings, and eligible terminal actions. For example, a cached delivered order makes return and exchange actions potentially eligible, while a cached pending order makes cancellation and pending-order modification actions potentially eligible. These hints are not trusted as final decisions; they expose ontology affordances to the LLM while leaving final admissibility to the verifier.

\subsection{Ontology-Derived Action Affordances}
Given grounded state $s_t$, the action layer can derive a set of currently meaningful action affordances:
\[
\operatorname{Afford}(s_t,\mathcal{O}) = \{a \in \mathcal{A} \mid \exists \theta,\ \operatorname{Enable}(a,\theta,s_t,\mathcal{O})\}.
\]
These affordances are symbolic hints, not hard plans. Their purpose is to make the ontology's state-dependent action space visible to the LLM. In the retail domain, the same order object affords different actions depending on whether its status is pending, delivered, cancelled, or already modified. This is the step that makes the method ontology-related in a planning sense: candidate actions are not retrieved only by lexical similarity, but induced from object class and state predicates.

\subsection{Action Proposal}
At step $t$, the LLM proposes a JSON action call:
\[
\hat{a}_t(\hat{\theta}_t) = \operatorname{LLM}(g,h_t,\phi(s_t),\mathcal{A}),
\]
where $\phi(s_t)$ is the compact ontology-grounded state abstraction. The prompt contains the ActionBank schemas, recent execution history, cached object summaries, and ontology-derived affordances. The LLM is therefore asked to choose within a semantically structured action space. It is not trusted as the final authority on executability; its output is treated as a candidate action instance that must be grounded and checked.

\subsection{Admissibility Verification}
Given a proposed action $\hat{a}_t(\hat{\theta}_t)$, the verifier applies five checks:
\[
V = V_{\text{exist}} \wedge V_{\text{param}} \wedge V_{\text{pre}} \wedge V_{\text{policy}} \wedge V_{\text{dup}}.
\]
\textbf{Action existence} checks whether the action id is present in ActionBank. \textbf{Parameter checking} verifies that required arguments are present and type-compatible when the type can be checked locally. \textbf{Precondition checking} evaluates state predicates such as \texttt{order.status == pending} or \texttt{order.status == delivered}. \textbf{Policy checking} enforces hard business rules such as user authentication and explicit confirmation before update actions. \textbf{Duplicate checking} rejects repeated information-gathering actions with identical arguments when a previous execution has already succeeded.

The verifier returns either \texttt{accept} or \texttt{reject} with one of five typed violations: \textsc{UnknownAction}, \textsc{MissingParameter}, \textsc{Precondition}, \textsc{Policy}, or \textsc{Duplicate}.
In the current implementation, duplicate-loop and confirmation checking are the easiest constraints to validate locally. This is a limitation of the present implementation, not a claim that these are the only useful verifier types.

This admissibility check is ontology-grounded in the following sense. The action id is resolved against an ontology action type, the target is checked against an ontology object class, the parameters are interpreted as typed role fillers, preconditions and effects are attached to object-state predicates, and policy constraints are represented as action-level guards. The verifier therefore does not merely ask whether the JSON call is syntactically valid; it asks whether the proposed operation is semantically meaningful for the target object in the current execution context.

\subsection{Repair Policy}
If verification fails, the proposed action is not executed and is not added to the successful execution trace. Instead, the system appends structured violation feedback to the prompt:
\[
( \hat{a}_t, \hat{\theta}_t, v, \phi(s_t), h_t ) \rightarrow \operatorname{repair\ prompt}.
\]
The repair prompt asks the LLM to propose a different productive action that satisfies all constraints. For duplicate lookup violations, the repair prompt explicitly instructs the LLM to use cached history results rather than transferring to a human agent. For missing confirmation, the expected repair is typically \texttt{ask\_for\_confirmation}. For failed preconditions, the expected repair is to choose an action compatible with the observed object state or to gather missing information.

Repair is bounded by a small retry budget. If no valid action is found, the agent falls back to \texttt{transfer\_to\_human\_agents}. This fallback is conservative, but it can also reduce final-action success when the verifier is too strict or when the LLM over-corrects after rejection.

\subsection{Repair Failure Analysis}
The same verifier trace is used to analyze repair behavior. For every rejected proposal, we record the rejected action, violation type, repaired action, whether the repaired action is accepted, and whether the final task outcome improves, remains unchanged, or degrades relative to Schema-Only. We classify repair outcomes into four categories:
\begin{itemize}
    \item \textbf{productive repair}: rejection causes the agent to choose a valid action that advances the task;
    \item \textbf{neutral repair}: rejection removes a violation but does not change final task failure;
    \item \textbf{over-correction}: rejection causes the agent to abandon a recoverable trajectory, usually by transferring to a human agent;
    \item \textbf{state-insensitive repair}: the repaired action remains incompatible with a counterfactual or dialogue-dependent state even though it passes local checks.
\end{itemize}
This analysis is necessary because local ontology consistency and task success are different properties. The evaluation therefore reports both executed violations and repair-induced outcome changes rather than treating successful verification as automatically beneficial for task completion.

\subsection{Execution Trace and Explanation}
For each episode, the system records accepted actions, rejected actions, violation types, repair attempts, and execution results. This trace supports two uses. First, it is used by the duplicate detector and state abstraction module. Second, it provides faithful explanations: the system can explain that an action was blocked because it repeated an already successful lookup, lacked user confirmation, or violated an order-status precondition. The explanation is therefore derived from verifier traces rather than generated as an unconstrained post-hoc rationale.

\section{Experimental Setup}
\subsection{Dataset}
We evaluate on the retail domain of $\tau$-bench~\cite{yao2024taubench}, a customer-service benchmark. The retail domain contains 500 users, 50 products, and 1,000 orders with 16 action types including authentication, query, cancellation, return, exchange, and modification. Each task provides a user scenario, evaluation criteria, and a gold action sequence. We use the official train/test split (74 train / 40 test tasks for retail).

$\tau$-bench is useful because it provides realistic stateful tool-use workflows, but it is not by itself sufficient to prove the ontology-specific claim of this paper. A high or low task score could be caused by language understanding, dialogue branching, model capability, simulator mismatch, or repair behavior. We therefore use $\tau$-bench in two complementary ways. First, the official retail test split is the end-to-end workflow benchmark. Second, we derive an ontology benchmark suite from the same domain objects, policies, tool schemas, and database states. The derived suite isolates whether the proposed action layer improves action grounding, state-sensitive affordance selection, argument-role binding, and effect-consistent execution.

\subsection{Benchmark Design}
The evaluation is organized around two questions. The first question is whether the agent completes realistic $\tau$-bench retail workflows. The second question is whether the ontology action layer contributes semantic information beyond ordinary tool schemas. The second question requires targeted tests, because ordinary task success does not reveal whether a model used object types, state predicates, role schemas, or effects.

Each case fixes the user goal and perturbs one ontology variable, such as order state, target object type, role filler, or expected effect. The state-sensitive affordance benchmark is the most direct test of the paper's ontology claim. For example, the same order mention should lead to different candidate actions when the order is \textit{Pending} rather than \textit{Delivered}. In a flat tool schema, both \texttt{cancel\_pending\_order} and \texttt{return\_delivered\_order\_items} are available as names. In the ontology action layer, the current object state changes the affordance set before the model proposes an executable action.

The argument-role and effect-consistency benchmarks test complementary parts of the representation. Role binding asks whether \texttt{order\_id}, \texttt{item\_ids}, \texttt{new\_item\_ids}, and \texttt{payment\_method\_id} bind to valid ontology individuals in the correct relation. Effect consistency asks whether the action selected by the agent corresponds to the intended state transition under local DB replay. Together, these tests show that ActionBank represents domain action semantics, not only blocking rules.

\subsection{Baselines}
\textbf{Schema-Only}: LLM receives the full ActionBank as a system prompt but has no runtime verifier. Actions are executed without constraint checking.

\textbf{VerifierNoRepair}: Schema-Only plus a blocking verifier. If a proposed action is non-admissible, the system transfers rather than asking the LLM to repair. This isolates the cost of blocking without recovery.

\textbf{VerifierRepair}: Schema-Only plus the runtime verifier and bounded repair loop. This is the clean test of the core action-layer contribution because it excludes retrieval, action suggestions, progress checks, and additional ontology context.

\textbf{VerifierRepairGrounded}: VerifierRepair plus deterministic argument grounding before verification. This isolates whether local grounding improves admissibility without changing the prompt architecture.

\textbf{OursFull}: The full engineered system: ActionBank, ontology context, state-derived action suggestions, argument grounding, progress checks, bounded repair, and train-case retrieval.

\textbf{Ontology Ablations}: Variants of OursFull that remove one ontology component at a time. \textsc{NoStatePredicates} keeps tool schemas and object types but removes state-derived affordances and precondition text from the prompt. \textsc{NoRoleGrounding} removes deterministic argument-role grounding. \textsc{NoEffects} removes expected effect descriptions from the action schemas and trace explanations. \textsc{NoAffordances} keeps the ActionBank but does not expose state-derived candidate actions to the LLM. These ablations are used for the ontology benchmark suite rather than as the main $\tau$-bench task-success table.

\subsection{Models}
We evaluate Kimi-latest (accessed via Kimi CLI, version as of June 2026), with temperature set to 0. Earlier pilot runs with open-weight models had lower final-action success and are not used as the main evidence in this paper.

\subsection{Metrics}
\textbf{Final-Action Success}: Predicted final action name matches the gold final action name. This is a proxy for task success; full $\tau$-bench task success requires dialogue simulation and NL assertion evaluation, which our current single-turn implementation does not support.
\textbf{Action Accuracy}: Prefix match between predicted and gold action sequences.
\textbf{Local DB-State Match}: Whether replaying the predicted action trace yields the same database hash as replaying the gold action trace. This is a local $\tau$-bench-style metric, not official $\tau$-bench reward.
\textbf{Strict Local Success}: Local DB-state match with no executed verifier violations, invalid actions, execution errors, unsupported NL-assertion criteria, or unsupported communication criteria.
\textbf{Executed Violation Count}: Number of violations observed in the executed trace. For Schema-Only, this is a post-hoc audit count (the same verifier is run after execution). For verifier-based methods, non-admissible proposals should appear as rejected rather than executed violations.
\textbf{Rejected Violation Count}: Number of violations blocked by the verifier before execution.
\textbf{Invalid Action Count}: Actions not in ActionBank or causing execution errors.
\textbf{LLM Error Trace Count}: Number of tasks whose step trace contains an LLM client error. Any nonzero value invalidates aggregate paper claims from that run.
\textbf{Repair Outcome}: Whether a rejected action leads to productive repair, neutral repair, or over-correction relative to Schema-Only.
\textbf{Execution Latency}: Average time per task.
\textbf{State-Sensitive Action Accuracy}: Accuracy on counterfactual pairs where the same goal and object mention require different actions because the object state changes, e.g., pending vs. delivered order.
\textbf{Affordance Recall and Precision}: Whether the ontology-derived affordance set contains the expected action and excludes actions that are incompatible with the current object state.
\textbf{Role-Binding Accuracy}: Whether action arguments bind to the correct ontology individuals and relations, including order ownership, item membership, replacement item validity, and available payment methods.
\textbf{Expected-Effect Match}: Whether the selected action's declared ontology effect matches the state transition observed under local DB replay.
\textbf{Ontology Ablation Delta}: Performance drop after removing object types, state predicates, role grounding, effects, or affordance hints. This is the main evidence that the ontology representation contributes more than a generic verifier.

\subsection{Verifier Check Results}

Although the invalid Kimi run cannot support task-performance claims, the symbolic verifier itself is tested independently of the LLM. The assertion-based verifier checks cover five admissibility cases:
\begin{itemize}
    \item update action without authentication is rejected by a policy constraint;
    \item return action on a pending order is rejected by an order-status precondition;
    \item exchange action without user confirmation is rejected by a confirmation constraint;
    \item correctly authenticated and confirmed cancellation of a pending order is accepted;
    \item duplicate successful lookup and unknown action ids are rejected.
\end{itemize}
These checks validate the implementation of the admissibility predicate, but they do not by themselves establish task-level agent performance. They are therefore reported as implementation validation rather than as benchmark results.

\subsection{Planned End-to-End Table}

After a valid 40-task run, the main table should compare at least three rows: \textsc{Schema-Only}, \textsc{VerifierRepair}, and \textsc{OursFull}. \textsc{VerifierRepair} isolates the core action-layer contribution, while \textsc{OursFull} includes ontology context, action suggestions, argument grounding, progress checks, repair, and train-case retrieval. The table columns should report final-name match, local DB-state match, strict local success, name-prefix action accuracy, executed verifier violations, rejected verifier violations, invalid actions, and LLM-error trace count.

This table is necessary but not sufficient for the ontology claim. It shows whether the full system helps on realistic workflows, but it does not isolate why. Until the corrected Kimi run is regenerated, we avoid claiming that the method improves task success or reduces executed violations on the 40-task split. The current paper claim is therefore methodological: the proposed action layer defines an inspectable ontology action semantics and an evaluation protocol that separates ontology grounding, execution compliance, and task completion.

\subsection{Qualitative Trace Analysis}

The trace format supports qualitative analysis once a valid model run is available. For each task, the logs record the proposed action, verifier decision, violation type, repair attempts, grounding changes, execution result, and local DB-state outcome. The intended qualitative analysis is to separate three cases: (1) the verifier blocks a harmful action and repair recovers progress; (2) the verifier blocks a harmful action but the model fails to recover; and (3) the verifier changes a previously successful trajectory and causes over-correction. We do not instantiate these cases with the excluded Kimi run because its traces are dominated by infrastructure-level LLM client errors.

\section{Discussion}
\subsection{What the Action Layer Contributes}
The primary value of the action layer is not higher autonomous planning success by itself. Its value is to provide an ontology-grounded semantics for agent actions. Compared with ordinary tool schemas, the action layer binds actions to ontology object types, parameter roles, state predicates, confirmation requirements, policy guards, effects, and execution-history predicates. This gives the agent a structured action space: it can ask which actions are meaningful for the current object state, what role each argument plays, what state transition the action should produce, and why a proposed action is inconsistent with the ontology.

This distinction also separates the proposed method from generic tool filtering. A filter can allow or deny a tool name; an ontology-grounded action layer represents the operation as a domain action over typed objects with preconditions and effects. The verifier is only one consumer of that representation. The same action layer also supports action affordance generation, argument grounding, state-aware prompting, repair feedback, and explanation. The key design principle is that agent planning should be grounded in domain actions and object states, not only in API syntax.

\subsection{Why Repair Requires a Separate Policy}
Ontology-grounded admissibility is a local semantic predicate: it can say why a proposed action is not meaningful in the current context, but it does not by itself choose the globally best next action. Post-rejection behavior is therefore a separate policy problem. In simple cases, the violation feedback maps directly to a local fix, such as inserting confirmation or using cached lookup results. In harder cases, the LLM may over-correct, abandon a recoverable trajectory, or choose an admissible action that is still wrong for the task. This suggests that future systems need a stronger repair policy, such as candidate-action ranking under admissibility constraints, state-machine-guided repair, or search over admissible actions, rather than relying only on a single LLM repair prompt.

\subsection{Limitations}
\textbf{Model capability.} The framework does not assume that the LLM is a reliable planner. The verifier can reject non-admissible local actions, but it cannot by itself infer the globally correct branch in a task with incomplete dialogue state or ambiguous user intent. Valid task-performance claims therefore require a clean model run and paired comparison against Schema-Only.

\textbf{Dialogue simulation.} $\tau$-bench tasks require back-and-forth dialogue for condition branching (e.g., ``if the agent asks for confirmation, only exchange the desk lamp; if asked again, do not exchange anything and return the water bottle''). Our current implementation uses a single-turn planner without dialogue simulation, leading to mismatches when user intent changes mid-conversation. The verifier cannot detect this because both branch actions satisfy their preconditions independently. Integrating with $\tau$-bench's dialogue simulator is essential for full evaluation.

\textbf{Repair overhead.} The repair loop increases latency because rejected proposals require additional LLM calls. Future experiments should report both ontology-consistency benefits and latency cost.

\textbf{Action layer completeness.} The proposed method depends on an action layer with explicit object classes, action types, role schemas, state predicates, preconditions, effects, and constraints. Many real systems lack such representations, motivating companion work on action extraction from procedural documents.

\subsection{Future Work}
We plan to: (1) regenerate the 40-task Kimi-latest results after LLM-client validation; (2) integrate with $\tau$-bench's dialogue simulator for full condition-branching evaluation; (3) conduct larger-scale counterfactual state tests to measure state sensitivity accuracy; (4) extend to the airline domain; (5) learn neural verifiers to complement rule-based checking; and (6) distinguish hard constraints from soft preferences.

\section{Conclusion}
This paper frames policy-constrained tool use as ontology-grounded action semantics for LLM agents. By representing operations as typed ontology actions with object bindings, role schemas, state predicates, preconditions, effects, constraints, confirmation requirements, and execution-history predicates, the action layer gives the agent more than a flat tool list. It supplies state-dependent action affordances, grounding checks, admissibility verification, repair feedback, and trace explanations. The current draft contributes the method, implementation, and reproducible evaluation protocol; valid aggregate task-performance claims require rerunning the corrected LLM client and auditing the generated paper metrics against raw traces. The framework should therefore be understood as an ontology action layer for agent planning and execution, not merely as a verifier wrapped around tools.
